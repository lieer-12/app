# Phase 5 维护接线契约

更新：2026-10-05。四模块、设置、导航、后台和备份维护已接入同一协调器；
实际验收结果见 `phase5-acceptance.md`，本文不是测试通过证明。

## 组件边界

- `DataGenerationRepository`：领域契约；数据实现严格读取本机元数据，提供数据库变更与世代递增的单个 Room 事务及观察流。
- `MaintenanceCoordinator`：Hilt 进程内单例；只管理许可、排空和维护会话，不读写业务实体，不执行文件选择或提醒重建。
- `LifeManagerDatabaseFactory`：Hilt 应用数据库的创建入口，提供显式迁移和默认初始化回调。Worker 通过应用 EntryPoint 取得真实共享仓库，不另开库，也不关闭应用数据库。没有 destructive migration。

现有 Manifest 没有独立组件进程，本协调器针对单进程。不能仅新建另一个协调器给后台用；后台接线必须取得相同 Hilt 单例。若将来增加多进程，须另行设计跨进程维护准入。

## 普通操作和旧结果

编辑器加载/打开时捕获世代，将令牌与该草稿或导航事件一起保存。不可在旧草稿最终保存时才捕获新令牌，尤其不能仅凭恢复后复用的 ID 判断草稿有效。

调用顺序为 `coordinator.run(oldToken) { moduleCoordinator.run { write + reminder work } }`。全局准入在已有模块 Mutex 之前；禁止在同一协程及其结构化子协程中重复获取全局准入。数据维护底座不会自动拦截直接 DAO/仓库写入，接线审计必须覆盖全部写入口。

`isCurrent(token)` 只用于瞬时检查，不是写/发布许可，不能解决“检查后再发布”的竞态。真正发布旧查询或导航结果须在同一次 `run(token) { publish }` 准入内完成。维护中 `isCurrent` 返回 false；调用方必须区分 `state != IDLE` 的临时冻结和世代真实改变：取消维护时仍须保留原草稿、延后发布未失效的结果，不能把暂时 false 当成删除草稿的命令。提交成功后的清稿/导航失效依据持久化世代变化；失败读取不能降级成默认 0。

## 维护会话

唯一公开的会话拥有者入口为 `withSession { session -> ... }`。内部获取立即设置 DRAINING、拒绝新准入，等待已经获得许可的操作全部结束后读取本机世代，进入 READY。不是把新写入排队到恢复后。等待取消或世代读取失败会解除该冻结，但不会取消原有写入，也不会推进世代。

文件选择/最终确认期间在该作用域内等待结果消息即可；不要用 `withMaintenance` 包住人机等待，也不要持有 Room 事务或模块锁等待。UI 回调将结果发给拥有者协程，不从另一个无关 Job 操作会话。短任务使用 `withMaintenance(session) { ... }`，它进入 RUNNING，验证会话、拥有者上下文与原世代，串行拒绝竞争会话任务。异常/取消后仍保持 READY，作用域最终退出自动释放至 IDLE，不暴露独立 begin/finish 让取消交付丢失会话。

内部在世代读取返回及交付前检查真实 Job 取消；获取后使用 `coroutineScope` 和 `withContext` 结构化执行会话主体，等待其子协程退出，finally 自动释放。上下文记录会话对应的作用域根 Job；进入维护任务前验证当前 Job 的真实父链归属，而不只验证可继承标记。测试覆盖读取恰好返回时取消、READY 等待时取消、RUNNING 子任务取消、替换 Job 绕过尝试及异常退出。GlobalScope/无关外部 Scope/替换为独立 Job 的任务即使继承会话标记也不能进入维护操作。沿用现有 coroutines 1.9.0，父链 API 显式选择 Experimental opt-in，没有升级依赖。

保护快照先在会话下读取；最终恢复/清空用 `generations.commit(session.generation) { database-only mutation }`，且必须在该全局维护会话内执行。业务写入、检查世代未被错误修改、推进世代都在同一 Room 事务中。世代上限/不匹配在执行 mutation 前拒绝。mutation 不能放文件或闹钟外部副作用，因为 Room 不能回滚它们。

成功提交后，原会话不能再次执行原世代的数据库任务；退出作用域仍会释放。提交后清理旧提醒在同一次 `withMaintenance` 中、数据库事务外完成；校准要在释放全局许可 / 会话后执行，不能嵌套重新获取普通许可。所有出口请求后台当前数据校准，非取消正常出口立即校准。数据提交与提醒结果分别报告；提交后的取消不表示数据库回滚。

## 数据边界和故障

本机世代不在备份载荷里，恢复不得重置它。新建 v5 和升级至 v5 使用初始化回调/显式迁移；普通设置读写不负责补建缺失世代。对既有 v5 缺失、负数、非 INTEGER 或溢出元数据拒绝维护，不为了继续运行而静默修复数据。若遇到此状态，需要单独诊断及明确修复方案。

维护状态/会话只是进程内状态。确认前进程死亡不重放事务，重启重新获取持久化世代；提交后依赖世代及应用启动安排的当前 Room 提醒校准。新 ViewModel、缓存残片和提交后校准有分层测试，不宣称真实设备强杀全部时序已验收。

## 当前测试范围

四个业务模块与设置接入共用 `ui/common/GenerationAccess`：读取快照前捕获令牌，在同一次许可内重新执行冷查询，并在 Main 发布快照；长驻 Room Flow 仅作失效通知，不能给缓存的旧 DTO 标记最新世代。结果发布及数据库写入均需要许可，不能只使用 `isCurrent`。错误结果遇到临时维护只等待发布，不重放数据库操作；提交后旧结果丢弃。

只读查询在准入间隙遇到 Busy/Stale 可重新捕获并读取；Busy 等待 IDLE，即使短暂冻结的中间状态被 StateFlow 合并，也不依赖另一次状态事件来恢复观察。重试有协程取消点，普通 `run` 写操作没有此重试。设置 `observeSettings`、`getSettings` 及更新均不补建默认行；默认行只由新建/迁移创建。既有 v5 缺失设置明确失败，更新在调用 transform 前拒绝，不能用默认偏好掩盖数据缺失。

元数据不可读的错误回退在 Main 再核对原快照标签，不能禁用已经发布的新世代页面；设置另外记录实际观察到的世代，防止新世代已到达但新偏好尚未读出时，旧回退将观察错误标记重新置为失败而阻断加载。

界面回调捕获该次渲染的普通不可变世代值；不在回调执行时重新读取 Compose 的 State 委托。习惯保存、输入、关闭和删除使用草稿世代，列表打开/打卡使用页面世代。冻结期间保留草稿；只有持久化世代改变才失效。设置币种本地草稿的 remember key 包含世代，即使恢复后的币种相同也不会沿用旧输入。习惯读写错误不让错误发布的再次世代读取失败逃出协程；元数据不可用时禁用写入。设置重新读取不自动重放失败选择。

协程测试覆盖准入/排空/取消、会话所有权、重入与并发任务、同 ID 陈旧令牌和读取失败；真实 Room 测试覆盖原子变更/回滚/竞争提交、Long 上限、损坏元数据及文件库重开。Android 用独立测试库验证初始化/持久化以及取消回滚、提交后同 ID 旧令牌拒绝。

待办、日程与订阅的渲染回调也绑定普通不可变世代；编辑器、冲突确认、订阅详情和扣费草稿在世代更换后失效。冷启动通知在页面尚无已验证快照时，立即尝试一次严格准入捕获，不在延迟执行时为旧事件补取新世代；临时冻结只延后原令牌的查询/发布。通知交接在原业务许可及模块锁释放后再执行，不能重复获取全局许可。

CSV 选择关联保存原世代和导出请求 ID，跨旋转/更换数据直到该次选择结果返回；迟到的取消/文件 URI 不清除新请求。真正外部文件 I/O 在准入验证后不占用维护许可；已开始的旧文件可完成，但旧结果不发布。文件选择和保存位置仍需设备人工验收，不承诺进程死亡后恢复导出。

## 第六批历史记录：导航和后台准入（2026-10-04）

以下“到达捕获”与尚未接线说明是当时边界，已由末尾 2026-10-05 规则替代。

Activity 的三类导航拥有者取得同一 `GenerationAccess`，到达时严格捕获世代；冻结中到达的新事件拒绝，不排队到恢复后。原请求经临时冻结仍可继续，真实世代变更使请求失效；迟到的消费确认不能清除较新的事件。导航图准备等待不持有许可，实际 Main 导航必须位于 `run(originalGeneration)` 内。目标页面/详情使用请求携带的原世代，不在业务交接时重新标记为新世代。

三类 Receiver 经共用 runner 进入同一个应用协调器：到达捕获原令牌，再在 IO 上准入，外层全局许可覆盖模块锁、数据库校验、闹钟变更及投递；Busy 快速结束并安排读取当前库的新校准，不保存或重放拒绝的广播载荷。PendingResult 在退出路径结束，元数据错误不能降级为 0。8 秒界限包围世代读取及投递全过程：元数据读取卡住也会取消并释放 capture 许可，不使维护一直等待。该卡住用例已从期望结束一次、实际未结束的 RED 转为 GREEN；最终全量为 530 JVM / 32 设备、APK 及 lint 通过，证据见 phase5-acceptance。

Worker 通过 Hilt EntryPoint 取得 `ReminderReconciler`，使用应用共享仓库/协调器，准入先于三个模块锁；Busy、陈旧令牌或读取失败返回 retry，普通协程取消继续抛出。Java 两参数构造保留给 WorkManager 默认反射工厂。启动及 Boot/时间/升级/精确权限变化只安排当前数据校准，不在广播生命周期内执行全库查询；并保留每日校准。

独立审查后即时队列使用 `APPEND_OR_REPLACE`，保留 RUNNING 期间到来的后续请求，按同一唯一名称串行执行，每轮重新读取当前 Room；不再承诺待运行事件合并。启动、系统事件和 Receiver 的 Busy 都可能追加任务，频繁事件有多轮执行代价。旧前置在入队时已经 FAILED/CANCELLED 可另起链；先追加、前置随后失败/取消仍可能按 WorkManager 依赖传播取消后续，前置 retry 时后续等待。每日校准仍保留；完整维护退出和进程死亡闭环尚未验收。

业务通知交接的请求身份同时绑定自身世代。旧快照失效不能取消已经携带当前世代的新请求；只有观察世代超过请求自身世代时才取消带标签请求，迟到的中间世代只清旧页面。实际许可内的 Main 通知发布先前移观察上下文、清除旧 DTO/草稿，再交付新目标。迟到的较旧观察上下文不得回滚该状态，也不能把旧列表重标成新世代。

这是到达/排队事件保护，不是完整载荷保护：Scheduler/通知点击 Intent 尚未携带世代；到达前就来自旧库、却在替换完成后才收到的旧广播仍无法识别。日程当前仍保留旧投递资格逻辑，完整 Room/开关/世代校验归 Task 6。文件维护工作流尚未存在，成功/取消/失败退出后的统一校准归 Task 5 接线，不能以 Busy 安排新 Worker 代替该闭环。

仍缺 SAF/保护文件/确认/全量替换 Use Case、载荷世代与提醒偏好、提醒退出校准和完整进程死亡验收。根主题/日期已有受保护设置 ViewModel 消费路径。四模块、导航及后台的局部测试不能代替真实文件恢复测试。

## 2026-10-05 当前源头载荷与退出规则

- 闹钟及通知点击 Intent 在产生时绑定原世代；Receiver 和 Activity 只使用载荷中的世代。
  未知 / 缺失 / 陈旧来源 fail closed，不按到达时世代重新标记；未知来源请求当前数据校准。
- Receiver 在共享全局许可内取得模块锁，重新读取 Room 和设置，核对当前资格；
  提示标题不可信。日程必须匹配实际发生时间、例外日期及未结束窗口。
- 被冻结的一次性闹钟以匹配世代 / 发生时间的操作提示供后续恢复，不保存待重放的业务载荷。
  业务读取 / 闹钟服务临时失败不提前消费待投递提示，每次重试仍重新验证 Room。
- `BackupMaintenanceWorkflow` 在保护文档写入并验证后独立最终确认，再单事务替换。
  同步清理旧提醒不重新取全局许可；会话 finally 释放后请求 WorkManager 当前数据校准。
  数据已提交而结果交接被取消时，持久化世代与 ViewModel 操作结果区分已提交状态。
- 提醒开关保存后释放普通许可再即时校准，并请求后台复核；后台和投递始终尊重当前设置。
  关闭权限不影响离线 CRUD，精确权限撤销采用非精确兜底。
