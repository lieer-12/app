## 3. 架构与组件职责

- `ui/settings`：`SettingsScreen`、`SettingsViewModel`、不可变 UI 状态、操作进度和确认事件；关于信息为真实版本及已核实的许可证说明。
- `domain`：设置模型与仓库接口、备份快照与验证规则、导出/预览/恢复/清空 Use Case、数据维护协调契约。领域层不依赖 Activity、文件选择器、DAO 或 Compose。
- `data/local`：设置及本机维护元数据 Entity/DAO、完整快照 DAO、显式迁移和事务实现。
- `data`：设置仓库、备份仓库、JSON 编解码器及文件流适配。备份 DTO 与数据库 Entity 分离，字段映射必须完整且有往返测试。
- Android 文件选择器、权限请求和生命周期刷新由 UI/平台适配层负责；平台层将操作结果交给 ViewModel/Use Case，不在页面中直接读写业务表。
- Hilt 装配组件；四模块继续共享同一 Room 数据库。只对恢复安全及设置接入所需的现有组件做定向调整，不作无关架构重写。

## 4. Room 迁移与设置规则

数据库升级至 v5：新增单行设置表和单行本机维护元数据表，提供明确的 `4 -> 5` migration，并保留已有迁移链。不得删除、重建或改写十张既有业务表的数据，不使用 destructive migration。

设置保存：

- 主题：跟随系统（默认）、浅色、深色；所有已实现页面、对话框及图表遵循所选主题。
- 日期格式：`yyyy-MM-dd`（默认）、`MM-dd-yyyy`、`dd-MM-yyyy`；仅影响展示，不改变 Instant/LocalDate 的存储及业务计算。
- 默认币种：初始 CNY，输入 ISO 4217 代码并沿用现有订阅金额规则校验；只用于后续新建订阅，不转换已有金额或改变现有统计口径。
- 待办、日程、订阅提醒开关：初始开启以保持既有行为；这是应用偏好，不等于系统已授予权限。
- 新建订阅默认提醒天数：初始为空集，保持既有新建行为；可配置 1/3/7 天组合或不选（不安排提醒），不批量改写现有订阅的独立提醒记录。

读取失败时呈现错误和重试，不把默认值当作成功读取并覆盖数据库。更新失败保留真实已保存状态。权限状态在应用返回前台后刷新；拒绝权限不影响离线 CRUD。

本机维护元数据保存数据世代编号，用于拒绝恢复/清空前产生的旧操作及提醒；它不属于用户偏好，不从备份文件中恢复。

## 5. 完整备份格式与导出

采用 UTF-8 JSON，首版格式版本为 1。包含格式标识、格式版本、源数据库版本、应用版本、导出时间、完整数据载荷及载荷 SHA-256 校验值。校验值仅检测损坏，不提供加密、来源认证或防篡改保证。

完整载荷包括：

1. `todos`、`tags`、`todo_tag_cross_ref`。
2. `schedules`、`schedule_exceptions`。
3. `habits`、`habit_records`。
4. `subscriptions`、`subscription_payments`、`subscription_reminders`。
5. 用户设置。

所有实际字段、主键、时间戳、排序、状态、未展示字段及关联必须保留。金额仍为 Long；Instant 使用 epoch milliseconds，LocalDate 使用 epoch days，与现有存储精度一致。不得用当前表单重新构建实体、重算历史或推断实际扣费。

Room 事务读取一致快照，文件写入在数据库事务之外完成。通过系统文件选择器保存用户选择的文件，不申请全盘存储权限，不在仓库保存用户备份。提醒系统缓存、系统权限、草稿、待消费导航事件和本机世代不导出。

导出前提示文件包含个人数据且未加密。仅在输出流关闭、文件可重新读取、格式和校验验证成功后报告成功。失败或取消不会修改数据库；如果提供方留下不完整文件，说明其不能用于恢复。

导入及可恢复导出限制为单文件 64 MiB、业务表合计 100,000 行。超限明确报错，不截断、不悄悄漏表。当前数据超限时不能声称已生成可恢复备份，也不能继续替换恢复。

## 6. 导入校验与完整替换恢复

不接受 CSV、SQLite 文件或未知备份格式。首版只接受 formatVersion 1 / schemaVersion 5 的完整备份；未来版本需另行增加明确兼容转换。

在写库前完成文件大小、JSON 类型、必需字段、版本、校验值、枚举/日期/时区可解析性、主键和联合键唯一性、外键引用、标签唯一约束及待办父子无环校验。未知业务字段拒绝导入，避免较新数据被静默丢弃。

结构合法的历史记录原样保存：例如现存的开始日期之前打卡记录仍应备份和恢复，不以当前“新增打卡资格”规则删除历史。可疑或不兼容数据只报告问题，不擅自修复原库。

恢复流程：

1. 用户选取来源文件；读取到受大小限制的应用临时区域并完整校验。预览四模块及关联记录数量，说明将替换业务数据和设置。
2. 告知未保存草稿不能合并，取得允许恢复并放弃草稿的确认。尚未提交时不直接销毁草稿。
3. 进入数据维护会话：等待已开始的写操作结束，冻结新的业务/设置写入和提醒投递；读取当前数据一致快照。
4. 要求用户为当前数据选择另一个备份文件，禁止使用与导入来源相同的 URI。成功写入并重新验证之前，恢复按钮不可用。
5. 最终二次确认明确显示完整替换影响、已验证的当前备份文件和来源摘要。确认等待期间仍保持维护冻结，不持有长期 Room 事务。
6. 在一个 Room 事务内按依赖顺序清除并插入数据，恢复所有主键和设置，并推进本机数据世代。数据库异常或提交前取消使整个事务回滚。
7. 提交成功后失效旧草稿、旧导航目标和异步结果，刷新四模块状态；清理旧提醒及已发布通知，按恢复后的数据和设置重建提醒。
8. 释放维护状态，展示结果，删除应用内部临时文件；不删除用户导入文件或成功导出的保护备份。

来源选择、校验、保护备份失败或最终确认取消均不得替换数据库。进程在确认前死亡，数据库不变，重启后从头开始；提交后的进程死亡由数据库世代和启动提醒校准处理，不自动重放恢复。

数据库恢复成功但提醒清理/重建失败时，明确报告“数据已恢复，但部分提醒处理失败”，安排后续校准；不错误地回滚已提交数据，也不报告全部成功。

## 7. 并发、草稿和提醒交接

统一的数据维护协调器覆盖四模块写操作、设置更新、备份替换、清空、Receiver、BootReceiver 和后台校准。既有模块协调器保留；嵌套锁顺序统一为全局操作协调后模块协调，禁止反向获取和重复获取非重入锁。

普通操作捕获当前数据世代，在实际写入前检查；维护期间拒绝新写入并呈现维护状态，不将其排队到恢复后执行。维护开始等待已进入的写入结束，防止保护备份之后又产生未备份的数据。

维护会话是进程内状态，不在等待文件选择或用户确认时长时间持有模块 Mutex。Receiver 遇到维护状态快速结束，不让广播等待人机交互；恢复成功、取消或失败退出会话后，均从当前数据库重新校准受影响提醒。Worker 通过可重试结果延后校准。

维护提交成功才推进世代并清除草稿；取消或数据库失败保留旧世代、数据和未提交草稿。异步查询、保存结果及导航事件按世代失效，不能把旧编辑状态套用到恢复后复用相同 ID 的实体。

待办、日程、订阅新闹钟携带本机世代；Receiver 投递前检查当前数据库、模块开关、实体资格和世代，不能仅相信广播标题/ID。升级前无世代的旧广播不直接投递，由启动校准重新排程。

关闭某类提醒时取消该模块闹钟和已发布通知；开启时从 Room 重建。重启、Worker 和恢复完成均尊重开关，不能重新打开已关闭的类别。精确权限缺失或被撤销采用既有安全非精确兜底，并向用户说明可能延迟。

这里的日程调整仅补充恢复安全所必需的投递前检查、世代和权限兜底，不宣称同时补齐全部重复提醒、全天策略或时间轴需求。

## 8. 清空、关于及错误状态

清空只删除四模块业务数据及关联记录，保留主题等用户设置。先说明范围并提供备份入口，再进行独立的最终确认；不把进入设置页或单次按钮点击当作清空授权。

清空沿用维护协调和单事务写入，成功后推进世代、清理草稿/导航/提醒。失败不清空一半的数据；闹钟服务失败与数据库失败分别报告。文件备份不随清空删除。

关于页展示真实 BuildConfig 版本、项目实际许可证状态和已核实的第三方许可证说明。不假定项目已有某种开源许可证，不伪造版权或加入无关外部跳转。

导出、读取、校验、保护备份、等待确认、提交、提醒校准分别有明确进度/错误状态；处理中阻止重复提交。错误可重试或安全退出，不吞数据库异常，不把取消显示为成功。
